A. Data platform architecture — Questions 1–5
Highest priority
1. Design a multi-tenant enterprise data platform from scratch.
Scenario: Multiple engineering, analytics and data-science teams need to ingest, transform, store and query data through a shared platform.
Discuss:
Overall architecture and major platform layers.
How teams onboard and manage their own pipelines.
Tenant isolation across compute, storage and metadata.
Resource quotas, workload prioritization and chargeback.
Common platform services versus team-owned capabilities.
SLOs and platform adoption metrics.
Principal-level follow-up: How would you evolve this architecture over 2–3 years without disrupting existing consumers?
Reference: Kubernetes — Multi-tenancy
2. Design a scalable enterprise data ingestion platform.
Scenario: Hundreds of source systems produce data through databases, APIs, files and application events.
Discuss:
Batch versus streaming ingestion.
Source connectors and onboarding framework.
Schema management and data contracts.
Retry, deduplication and idempotency.
Backpressure and failure recovery.
Monitoring ingestion latency and throughput.
Follow-up: How would you support thousands of pipelines without creating operational overhead?
Reference: Apache Kafka Documentation
3. Design a Change Data Capture (CDC) platform using Debezium and Kafka.
Scenario: Capture changes from MySQL, PostgreSQL and MongoDB and make them available to downstream consumers.
Discuss:
Database log-based CDC.
Debezium connectors and Kafka topics.
Initial snapshot and incremental changes.
Ordering and delivery guarantees.
Duplicate events and idempotent consumers.
Schema evolution and deleted records.
Connector failure and recovery.
Follow-up: How would you perform a consistent initial snapshot while the source database continues receiving writes?
Reference: Debezium Documentation
4. Design a real-time analytics platform using Kafka and Flink.
Scenario: Process billions of events and expose near-real-time business metrics.
Discuss:
Event ingestion and partitioning.
Event-time versus processing-time.
Watermarks and late-arriving events.
Stateful stream processing.
Checkpointing and recovery.
Exactly-once processing semantics.
Serving results to analytical databases.
Follow-up: What happens when one Kafka partition becomes extremely hot?
References: Apache Flink · Apache Kafka
5. Design a unified batch and streaming data architecture.
Scenario: An organization needs historical batch processing and real-time analytics using the same data foundation.
Discuss:
Lambda versus Kappa architecture.
Batch and streaming ingestion paths.
Shared storage and data contracts.
Consistency between batch and streaming outputs.
Reprocessing historical data.
Avoiding duplicate business logic.
Follow-up: How would you handle a correction to historical data without corrupting the real-time pipeline?
References: Apache Spark · Apache Flink

3. Which five should you master first?
I recommend starting with these five. Together, they cover most of the central responsibilities described in the job listing.
Priority 1
Must master
1. Multi-tenant enterprise data platform
Demonstrates end-to-end architecture, platform thinking, tenant isolation and technical direction.
2. CDC platform using Debezium and Kafka
Demonstrates your understanding of distributed ingestion, consistency, ordering and failure recovery.
3. Iceberg-based lakehouse
Demonstrates modern data storage, table formats, metadata, partitioning and concurrent workloads.
4. Real-time analytics using Kafka and Flink
Demonstrates streaming architecture, state management, fault tolerance and latency trade-offs.

Demonstrates Principal-level thinking about availability, disaster recovery, consistency and cost.
My recommendation is to prepare Questions 1–10 in greater technical depth, then Questions 11–20 with equal attention to architectural reasoning, trade-offs and operational ownership.
4. How to answer a 60-minute system-design question
Don't immediately start drawing boxes and arrows. Use this interview structure.
Time
What you should do
0–5 min
Clarify requirements and business problem
5–10 min
Estimate scale and define non-functional requirements
10–20 min
Draw high-level architecture
20–35 min
Deep dive into critical components
35–45 min
Discuss scaling, reliability and failure scenarios
45–55 min
Explore cost, security and trade-offs
55–60 min
Summarize decisions and future improvements

Your architecture checklist
For every question, make sure you cover these areas:
Functional requirements: What must the system do?
Non-functional requirements: Throughput, latency, availability, durability and security.
Scale: Events per second, TB/day, number of tenants, pipeline count, query concurrency.
Architecture: Components, interfaces and data flow.
Data model: Partitioning, indexing, schema and storage format.
Reliability: Retries, idempotency, recovery, replication and disaster recovery.
Observability: Metrics, logs, traces and alerts.
Cost: Storage, compute, network and operational overhead.
Trade-offs: Why this design instead of alternatives?
Evolution: How would you migrate and scale it over time?
Principal-level differentiator: Always discuss who owns each platform capability, how other teams adopt it, how standards are enforced, and how you measure whether the platform is successful.
