# Mock Interview 5 — Instagram-Like Social Media Analytics Platform

**Interview level:** Staff / Principal Data Engineer  
**Suggested duration:** 90 minutes  
**Primary challenge:** Model a high-volume social graph and engagement platform while balancing event scale, feed exposure, privacy, deletion, approximate analytics, and rapidly evolving product definitions.

## 1. Interview brief

> Design a data platform for a social application with users, accounts, posts, stories, reels, follows, impressions, likes, comments, shares, saves, sessions, and creator analytics. Product teams need engagement, reach, retention, feed quality, creator growth, and safety metrics.

This is not simply a "posts and likes" schema. The hardest issues are event volume, what counts as an impression, identity/privacy changes, relationship history, and the difference between content creation and content distribution.

## 2. Requirements discovery

Ask:
- Are accounts private/public? Can users block or restrict each other? Yes.
- Can a post be edited, archived, deleted, or made private? Yes.
- Is an impression counted when rendered, visible for a threshold, or watched for a duration? Product definition required.
- Are views deduplicated per user/session/day? Different metrics may exist.
- Are follows directional? Yes: follower → followee.
- Can a user follow and unfollow repeatedly? Yes.
- Are likes/comments/shares mutable or removable? Yes; preserve events and current state.
- Are feed impressions generated by ranking/recommendation services? Yes.
- What scale? Illustrative: billions of engagement and impression events per day.
- What freshness? Near-real-time creator dashboards; daily trusted reporting.
- What privacy rules apply? Deletion, blocking, private account visibility, regional retention, and access controls.

## 3. Process and grain matrix

| Process | Fact | Grain |
|---|---|---|
| Content lifecycle | `fact_content_event` | One row per content event/version |
| Feed exposure | `fact_content_impression` | One row per qualified impression event |
| Engagement | `fact_engagement_event` | One row per like/comment/share/save event |
| Current engagement state | `fact_engagement_state` | One row per user × content × engagement type |
| Follow graph changes | `fact_follow_event` | One row per follow/unfollow/block event |
| Current graph snapshot | `bridge_user_follow_current` | One row per active follower → followee edge |
| Session activity | `fact_session` | One row per session |
| Creator daily metrics | `fact_creator_content_daily` | One row per creator × content × date |
| User retention | `fact_user_activity_daily` | One row per user × date × activity definition |

An impression is not a unique viewer. A unique viewer is a deduplicated aggregation over a defined time window and identity policy. A like state is not the same as a like event.

## 4. Conceptual model

```text
USER ──< CONTENT (POST / REEL / STORY)
 │             │
 │             ├──< IMPRESSION_EVENT
 │             ├──< ENGAGEMENT_EVENT (LIKE / COMMENT / SHARE / SAVE)
 │             └──< CONTENT_VERSION / MODERATION_EVENT
 │
 ├──< FOLLOW_EVENT >── USER
 ├──< BLOCK_EVENT  >── USER
 └──< SESSION ──< SESSION_EVENT

CREATOR ──< CONTENT
CONTENT ──< HASHTAG / TOPIC (many-to-many bridge)
```

The social graph is naturally many-to-many. A current bridge is useful for current-state joins; the event fact is necessary for historical follow growth and churn. Do not confuse a bridge table with a factless fact: the bridge represents a relationship; a factless event fact records an occurrence.

## 5. Dimensions and privacy-aware identity

- `dim_user`: pseudonymous stable user key, account cohort, locale, approved status attributes.
- `dim_content`: content type, creation time, creator key, visibility class, topic/category.
- `dim_device`, `dim_app_version`, `dim_surface`, `dim_feed_context`.
- `dim_date`, `dim_country`, `dim_language`.
- `dim_engagement_type`, `dim_moderation_reason`.
- `bridge_content_topic`: content-to-topic many-to-many relationship.
- `bridge_user_follow_current`: active follower/followee edge with effective start.

Use a stable internal surrogate key that is not a public username. Usernames can change and can be recycled. Identity mappings and deleted-user handling require restricted access.

## 6. Fact design

### `fact_content_impression`
**Grain:** one qualified impression event, as defined by product instrumentation.  
Fields: event ID, viewer key, content key, creator key, event time, surface, feed/ranking request ID, position, dwell duration, qualification rule version, experiment assignment. Preserve both raw exposure and qualified impression if definitions differ.

### `fact_engagement_event`
**Grain:** one engagement action event.  
Fields: event ID, user key, content key, action type, event time, source surface, client/server origin, event version, reversal/deletion reference. A like then unlike yields two events; current state is derived.

### `fact_follow_event`
**Grain:** one follow/unfollow/block/unblock event for a directed user pair.  
A user can follow another, unfollow, and follow again. Do not impose one event per pair. Current graph is a derived state.

### `fact_creator_content_daily`
**Grain:** creator × content × reporting date × metric-definition version.  
Measures: qualified impressions, unique viewers (approximate or exact policy), likes, comments, shares, saves, watch seconds, completion counts. This is a serving aggregate; preserve source facts and metric definitions.

## 7. Metric semantics

Potential metrics:
- Reach = distinct eligible viewers exposed to content over a window.
- Impressions = qualified exposure events.
- Engagement rate = selected engagement actions / selected exposure denominator. Name exact numerator and denominator.
- Watch time = sum of eligible playback intervals with deduplication and session rules.
- Follower growth = follows minus unfollows over a period; current follower count is an end-of-period snapshot.
- Retention = users active in cohort period N / eligible cohort users, with activity definition and timezone.

**Interviewer:** "Why does creator reach differ from impressions?"  
**Candidate:** "One person may see the same content multiple times. Impressions count qualified events; reach counts distinct viewers under a defined identity and window policy. Both are useful and must not be conflated."

## 8. SQL examples

### Engagement events by content
```sql
SELECT content_key, CAST(event_ts AS DATE) AS event_date,
       SUM(CASE WHEN action_type = 'LIKE' THEN 1 ELSE 0 END) AS like_events,
       SUM(CASE WHEN action_type = 'COMMENT' THEN 1 ELSE 0 END) AS comment_events,
       SUM(CASE WHEN action_type = 'SHARE' THEN 1 ELSE 0 END) AS share_events
FROM fact_engagement_event
WHERE event_ts >= :start_ts AND event_ts < :end_ts
  AND is_valid_event = TRUE
GROUP BY content_key, CAST(event_ts AS DATE);
```
If the KPI is current likes, query the current engagement state, not raw like events.

### Current follower count
```sql
SELECT followee_user_key, COUNT(*) AS current_followers
FROM bridge_user_follow_current
WHERE is_active = TRUE
GROUP BY followee_user_key;
```

### Daily creator engagement rate
Aggregate impressions and engagements separately to creator/content/date grain, then join. Do not join raw impressions to raw engagement events: if content has 10,000 impressions and 300 engagements, a raw many-to-many join can produce millions of rows.

## 9. Scale and architecture

Illustrative architecture:
- Mobile/web clients and backend services emit versioned events.
- Kafka/MSK or equivalent buffers high-volume streams.
- Bronze object storage retains approved raw events with access and retention controls.
- Stream processing computes low-latency counters and anomaly signals.
- Lakehouse/warehouse batch jobs produce corrected, auditable daily aggregates.
- OLAP serving store supports creator dashboards and product analytics.
- Feature pipelines publish governed features to ranking/ML systems with freshness and point-in-time correctness.

Design for skew: celebrity content may receive disproportionate impressions. Avoid partitioning or sharding all data by creator ID alone. Use event-date partitioning plus distribution/clustering strategies; consider salting/hierarchical aggregation for hot keys.

Use approximate distinct counting for exploratory/high-scale dashboards only when error bounds are accepted. Finance, safety, or contractual metrics may require exact or reconciled counts.

## 10. Privacy, deletion, and access

Deletion is a data lifecycle workflow, not a `DELETE FROM dim_user` operation. Identify:
- raw event stores;
- derived aggregates and snapshots;
- search indexes and caches;
- feature stores and training datasets;
- downstream exports and partner systems;
- backups and retention exceptions.

Maintain deletion tombstones and dependency lineage. Recompute aggregates where individual contributions must be removed; where policy permits irreversible aggregation, document thresholds and privacy review. Blocked/private relationships affect visibility and eligible analytics. Avoid exposing user-level interaction histories broadly.

Meta engineering material on data understanding and automated data removal illustrates why privacy metadata, asset lineage, dependency tracking, and coordinated deletion matter at scale.

## 11. Interview dialogue

**Interviewer:** "A user likes a post and then unlikes it. What is the count?"  
**Candidate:** "The event history has two events; the current-state table has no active like. We must label event volume versus current likes."

**Interviewer:** "The same post is shown five times to one viewer."  
**Candidate:** "Five qualified impressions if each meets the definition; one unique viewer for the chosen window. If product defines one impression per session, apply that qualification rule version."

**Interviewer:** "A creator deletes a post. Do we delete every metric?"  
**Candidate:** "We follow deletion policy and purpose-specific retention. The content record may be tombstoned, derived personal data removed or recomputed, and only policy-approved aggregates retained. The lineage graph identifies downstream copies."

**Interviewer:** "A celebrity account has 100 million followers and a post goes viral. How do you avoid a hot partition?"  
**Candidate:** "I would avoid a single creator key as the sole distribution key. Use time-based partitioning, multi-stage aggregation, salting or key splitting for hot keys, and monitor skew. The right strategy depends on query patterns and the compute engine."

## 12. Principal-level probes
1. How do you establish event contracts across mobile, feed ranking, and backend services?
2. How do you define qualified impression consistently across product versions?
3. How do you handle client retries and duplicate events?
4. How do you support point-in-time features for ranking models?
5. How do you reconcile low-latency counters with corrected warehouse metrics?
6. How do you execute user deletion across derived data and ML pipelines?
7. How do you prevent analytics access from bypassing privacy restrictions?
8. How would you migrate event schemas without breaking long-lived dashboards?

## 13. Common mistakes
- Treating reach and impressions as equal.
- Treating likes as immutable facts or counting like/unlike events as current likes.
- Modeling follow relationships as a single static user attribute.
- Joining raw impression and engagement events directly.
- Ignoring celebrity skew and hot keys.
- Using exact distinct counts everywhere without cost analysis.
- Treating deletion as a single-table operation.
- Failing to version metric qualification rules.

## 14. Practice exercise

A reel receives 1 million impressions, 300,000 unique viewers, 80,000 likes, 10,000 unlikes, 4,000 shares, and 15,000 comments. The creator deletes it after 30 days; 5% of viewers are in a jurisdiction with a stricter retention requirement.

Design:
- event and current-state facts;
- reach and engagement-rate definitions;
- high-cardinality aggregation strategy;
- deletion propagation;
- historical metric correction;
- access policy for creator and internal analytics.
